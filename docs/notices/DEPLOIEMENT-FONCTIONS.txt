BAOBABS BASKET CLUB — Les fonctions serveur
===========================================

LE PIÈGE, ET IL EXPLIQUE TOUT
  Une fonction Supabase a DEUX noms.

    · « Name »  — l'étiquette affichée dans la liste. On la choisit, on
                  peut la changer, elle ne sert qu'à s'y retrouver.
    · le SLUG   — ce qui forme l'URL. Créée depuis l'éditeur du tableau
                  de bord, la fonction reçoit un slug TIRÉ AU SORT :
                  bright-endpoint, hyper-processor, swift-api…

  On déploie donc consciencieusement une fonction nommée
  « envoi-newsletter », le tableau de bord l'affiche sous ce nom — et
  elle répond en réalité à /functions/v1/bright-endpoint.

  L'administration, qui appelle un nom précis, recevait un 404 : le même
  résultat que si rien n'avait été déployé. La liste disait « c'est là »,
  la mesure disait « ça n'existe pas », et les deux avaient raison.

  Le slug se lit dans la colonne URL de la liste des fonctions, ou dans
  le fil d'Ariane quand on ouvre une fonction.

CE QUI RESTE À FAIRE
  1. CONFIRMATION-RESERVATION N'EXISTE NULLE PART. C'est l'e-mail envoyé
     au supporter quand il réserve un billet. Le site l'appelle et
     n'obtient rien — la réservation est bien enregistrée et la référence
     s'affiche, seul l'e-mail manque. Le code est prêt dans
     supabase/functions/confirmation-reservation/.

  2. SWIFT-API ET HYPER-PROCESSOR SONT LA MÊME FONCTION, déployée deux
     fois (à quinze jours et trois jours). La plus ancienne peut être
     supprimée — mais vérifiez d'abord qu'aucun déclencheur de la base
     ne l'appelle encore, sinon les alertes d'inscription cesseraient
     sans un mot.

  3. LES SECRETS BREVO, sans lesquels une fonction déployée répond mais
     n'envoie rien : BREVO_API_KEY, BBC_SENDER_EMAIL, et si l'on veut
     BBC_SENDER_NAME. Supabase → Edge Functions → Secrets.
     Ne les mettez jamais dans un fichier du dépôt.

  4. DEPOT-PIECE EST APPELÉE PAR LE SITE ET N'EXISTE PAS. C'est la
     fonction qui reçoit les papiers que la famille photographie depuis
     « Suivre mon inscription ». index.html l'appelle en dur ; elle
     répond 404. La page encaisse proprement — « L'envoi n'a pas abouti
     — réessayez, ou apportez la pièce au club » — mais l'envoi
     n'aboutira jamais. Et le tutoriel promet la fonctionnalité :
     « Les pièces peuvent arriver toutes seules. »
     Le code est prêt dans supabase/functions/depot-piece/.

  5. RIEN NE DÉCLENCHE L'ALERTE D'INSCRIPTION. La fonction est déployée
     et vivante (hyper-processor), mais personne ne l'appelle : ni la
     base, ni le site, ni l'admin. Une inscription attend donc qu'on
     pense à ouvrir l'admin — alors que la page promet un rappel sous
     48 h. Voir la section suivante.


QUE LES INSCRIPTIONS ARRIVENT DANS LA BOÎTE DU CLUB
  Tout est écrit et déployé. Il manque UNIQUEMENT le déclencheur : un
  webhook de base de données. Trois minutes, aucun code.

  1. LE SECRET DE DESTINATION
     Supabase → Edge Functions → Secrets → Add new secret
       Nom   : BBC_ALERT_EMAIL
       Valeur: l'adresse du club. Plusieurs adresses possibles,
               séparées par des virgules.
     Sans lui, l'alerte part sur BBC_SENDER_EMAIL — ce qui marche
     aussi, mais mélange l'expéditeur et le destinataire.

  2. LE WEBHOOK
     Supabase → Database → Webhooks → Create a new hook
       Name       : alerte-inscription
       Table      : academy_registrations
       Events     : Insert  (Update et Delete décochés)
       Type       : Supabase Edge Functions
       Edge Function : celle dont le slug est hyper-processor
       Method     : POST
     Laissez les en-têtes par défaut : Supabase y met sa clé de
     service, et c'est ce que la fonction attend.

  3. L'ESSAI
     Déposez une inscription depuis le site avec un nom d'essai. Elle
     doit arriver par e-mail en quelques secondes, avec la référence et
     le téléphone dans l'objet. Puis supprimez le dossier d'essai dans
     l'admin.
     Si rien n'arrive : Database → Webhooks → la colonne des envois
     récents dit le code de réponse. Un 500 « BREVO_API_KEY manquant »
     veut dire que le point 1 des secrets n'est pas fait.

  POURQUOI UN WEBHOOK ET PAS UN APPEL DEPUIS LE SITE
  La fonction relit la ligne dans la base à partir du seul identifiant :
  ce qui part par e-mail vient toujours de la base, jamais du corps de
  la requête. Appelée depuis le site, elle resterait sûre — mais
  n'importe qui pourrait faire renvoyer l'alerte en boucle. Le webhook
  part du serveur : personne d'autre ne peut le déclencher.


DÉPLOYER AVEC UN SLUG LISIBLE — LA LIGNE DE COMMANDE
  C'est la seule façon d'obtenir un slug qui soit le nom : déployée
  ainsi, la fonction prend le nom de son dossier.

  Un terminal ouvert DANS le dossier du site :

      npx supabase login
      npx supabase link --project-ref lmwbwasupqkvswukieav
      npx supabase functions deploy

  La dernière commande envoie les quatre fonctions rangées dans
  supabase/functions/ (envoi-newsletter, confirmation-reservation,
  alerte-inscription, aide-redaction), chacune sous son propre nom.

  Le mot de passe demandé au « link » est celui de la BASE DE DONNÉES
  (Project Settings → Database), pas celui de votre compte.

  Une fois cela fait, remettez les vrais noms dans la table FN de
  admin-matchs.html — le commentaire qui l'accompagne le rappelle.


VÉRIFIER SANS RIEN ENVOYER
  L'écran Newsletter interroge la fonction à chaque ouverture. Tant
  qu'elle ne répond pas, un bandeau orange s'affiche ; il disparaît tout
  seul dès qu'elle répond. Cela ne coûte pas un e-mail.

  En ligne de commande :
      npx supabase functions list
